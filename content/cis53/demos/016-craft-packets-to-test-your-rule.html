Craft packets to test your rule (and find what it misses)

One Suricata rule looks for a GET to /api/v1/poll?id=. A Scapy script writes seven versions of that request into a pcap file: whole, split mid-word, out of order, percent-encoded, with a doubled slash, in capitals, and a harmless one. Nothing is sent on any network. Which ones does the rule see?

Download and open

  • class5-scapy-rule-test.py — writes class5-variants.pcap offline (pip install scapy)
  • class5-test.rules — the one rule under test

01Build the test traffic.

pip install scapy
python class5-scapy-rule-test.py
Answer

The script writes class5-variants.pcap: 51 packets, seven TCP conversations on source ports 41001 to 41007. It builds each handshake by hand, then places the request bytes into one, two or reordered segments. It uses wrpcap only; there is no send(). In a lab, sending crafted packets is only allowed to hosts you were given, which is why the NetLab Scapy lab runs on its own virtual network.

02Run the rule and predict first.

suricata -r class5-variants.pcap -S class5-test.rules -l out -k none
grep -o '10.0.0.31:410[0-9]*' out/fast.log | sort
Answer

Before you run it, write down which ports you expect. The result: ports 41001, 41002, 41003, 41004 and 41005 alert; 41006 (capitals) does not; 41007 (the benign request) correctly stays quiet.

  • 41002 and 41003: Suricata reassembles the TCP stream, so a request split mid-word or delivered out of order is still seen.
  • 41004: http.uri is normalized, so %6f is decoded to o.
  • 41005: the doubled slash is normalized away.

03Fix the miss and prove the fix.

sed 's/content:"\/api\/v1\/poll?id="; startswith;/content:"\/api\/v1\/poll?id="; nocase; startswith;/' class5-test.rules > fixed.rules
suricata -r class5-variants.pcap -S fixed.rules -l out2 -k none
grep -o '10.0.0.31:410[0-9]*' out2/fast.log | sort
Answer

The content match is case-sensitive, so /API/V1/POLL slipped past. Adding nocase catches port 41006. Now rerun the benign request: it must still be quiet. A fix that adds a false positive is not a fix. Note that a server may or may not treat the capital path as the same URL; asking what the real server does is a detection-engineering question, not only a rule question.

04Add one variant of your own.

# edit class5-scapy-rule-test.py: add conversation(41008, [(0, REQ % b"/api/v1/poll?id=a1b2c3d4&x=1")]) and similar
python class5-scapy-rule-test.py && suricata -r class5-variants.pcap -S fixed.rules -l out3 -k none
Answer

Try a trailing parameter, a different method (POST), a space-padded header, or HTTP/1.0 without a Host header. Each one is a hypothesis about how an attacker or a sloppy client might differ. Keep a table of variants and results; that table is the validation record Roddie Ch. 9 asks for.

05Where does this fit in a real program?

# Roddie Ch. 9: Atomic Red Team runs small tests per ATT&CK technique;
# CALDERA runs multi-step operations; both then check whether the detection fired.
Answer

Crafting packets tests one rule by hand. Atomic Red Team and CALDERA, the tools in Roddie Ch. 9, run actual adversary techniques on test hosts and check whether your detections fire, so you can measure coverage across many techniques instead of one rule. The method is the same: write the test, predict the result, run it, record what you missed.
