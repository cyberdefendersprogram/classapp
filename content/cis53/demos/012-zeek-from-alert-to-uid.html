Zeek: from an alert to the whole story

Same capture as Demo 11. An alert says 10.0.0.77:52001 sent something out at 09:01:00. Turn the capture into Zeek logs and rebuild what happened without opening a single packet.

Download and open

  • rule-lab.pcap — the same capture used in Demo 11

01Make the logs.

mkdir zeek-out && cd zeek-out
zeek -C -r ../rule-lab.pcap
ls
Answer

You get conn.log, dns.log, http.log, files.log, ssl.log and packet_filter.log. -C skips checksum checks (captures taken on a host often have bad ones). One line per connection or event, tab separated, joined by uid.

02Find the session the alert pointed at.

zeek-cut uid id.orig_h id.orig_p id.resp_h id.resp_p service orig_bytes resp_bytes duration conn_state < conn.log | awk '$2=="10.0.0.77" && $3==52001'
Answer

uid CwGZhJ1x7YZ0f0RK72 (yours will differ in other runs), 10.0.0.77:52001 to 198.51.100.77:80, orig_bytes 63305 and resp_bytes 70: a large upload with a tiny reply. conn_state SF means a normal complete connection. The uid is your key for every other log.

03Read the same uid in http.log.

zeek-cut uid method host uri user_agent request_body_len status_code < http.log | grep CwGZhJ1x7YZ0f0RK72
Answer

POST to host files.cdn-sync.test, uri /upload?name=customers.csv, body 63138 bytes, status 200, user agent python-requests/2.31.0. Now you know the file name and that the server accepted it.

04Who asked for that name, and when?

zeek-cut ts id.orig_h query qtype_name answers TTLs < dns.log | grep cdn-sync
Answer

10.0.0.77 asked for it once about half a second before the upload and once again before the TLS session. The answer is 198.51.100.77 with a TTL of 60. Nobody else in the office ever looked it up (check with zeek-cut id.orig_h query < dns.log | sort | uniq -c). A new name that only one host contacts is a good enrichment lead.

05Is it a beacon?

zeek-cut ts uri < http.log | grep check | awk 'NR>1{printf "%.0f ", $1-p} {p=$1} END{print ""}'
Answer

Seven intervals, all 60 seconds. Humans do not click that evenly. Compare with zeek-cut orig_bytes < conn.log for the same host: every beacon sends 111 bytes. Regular timing and a fixed size are the I/O-graph pattern from Week 2, now as a query. Real malware adds jitter, so look for low variance rather than exact equality.

06Find the encrypted copy.

zeek-cut uid id.orig_h id.resp_h id.resp_p server_name version < ssl.log
zeek-cut uid orig_bytes resp_bytes < conn.log | grep CN60ng1uRb7C7Ncw7h
Answer

ssl.log shows server_name files.cdn-sync.test over TLSv13 from 10.0.0.77. conn.log for that uid: 52283 bytes out, 3543 back. Zeek cannot read the contents, but it kept the name, the sizes and the timing, which is the argument for keeping these logs longer than full packets (Bejtlich Ch. 9; Roddie Ch. 4, data sources).

07Write the triage note.

Scope:  which host, user, time window?
Enrich: what is the destination, has anyone else seen it?
Decide: benign, suspicious or confirmed?
Record: what did you look at, what did you decide, what next?
Answer

Example: "10.0.0.77 posted a 63 kB customers.csv to files.cdn-sync.test (198.51.100.77) at 09:01:00 PT, beaconed every 60 s eight times, and sent about 52 kB to the same name over TLS at 09:10:40. The name was first queried by this host. Confirmed exfiltration. Next: isolate the host, identify the process, check what read customers.csv (see Demo 13)." Note which statements are evidence and which are inference.

Discuss

  • Which log would you keep longest if storage were tight, and why? (conn.log is small and answers "who talked to whom, how much".)
  • What would change if the upload had only ever happened over TLS? What question could you still answer?
  • Where does the Suricata alert fit, if the Zeek logs already tell the whole story? (An alert tells you where to start looking.)
