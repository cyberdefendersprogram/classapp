Class 3 demo · DNS

DNS: tunnel, DGA and fast flux

One 8-minute capture of an office resolver. Four hosts behave normally. Two more are doing something else, and one name is quietly changing its answers. Find all three. This is the signal-versus-noise skill from Class 2, applied to one protocol.

Download and open

  • dns-tunnel-dga.pcap — 284 packets: normal lookups, a DNS tunnel, a DGA host and a fast-flux name

All traffic is synthetic. Hosts use private or documentation addresses and domains end in .test or .example. Nothing in the file is real malware.

01Who is asking, and what is normal?

Statistics > Conversations > UDP
Statistics > DNS
dns.flags.response == 0
Answer

Six clients talk to the resolver 10.0.0.2. Hosts .11, .12 and .13 each send 17 or 18 short A and AAAA queries for names like mail.office.test with TTLs of 300 to 3600. That is the baseline. Hosts .14 (32 queries), .31 (45) and .77 (13) do not match it.

02Find the long names.

dns.flags.response == 0 && dns.qry.name.len > 50
Answer

13 queries, all from 10.0.0.77, all type TXT (16), all to *.t.updates-cdn.test. Each has a counter label (000 to 012) and a 52-character label of letters and digits. Normal names in this file are under 30 characters. One parent domain with 13 unique child names is the tunnel signature.

03Decode the payload.

tshark -r dns-tunnel-dga.pcap -Y 'dns.qry.name contains "t.updates-cdn.test" && dns.flags.response==0' -T fields -e dns.qry.name
# join the second label of every line, upper-case it, add = padding, base32-decode
Answer

The text starts employee,salary,ssn followed by rows of synthetic people. Anything a tunnel can encode can leave this way: it is data exfiltration inside a protocol that firewalls usually allow. Notice the answers: TTL 0 and the string ok, so the resolver cannot cache them and every chunk reaches the attacker's name server.

CyberChef (From Base32) does the same decode if students prefer a browser.

04Find the NXDOMAIN storm.

dns.flags.rcode == 3
Statistics > Conversations, then sort by packets
Answer

44 NXDOMAIN answers, all to queries from 10.0.0.31. Names are 11 to 15 random letters such as ydrgjcpajocqoi.test. That is a domain generation algorithm (DGA) looking for its command server. One name resolved: bryvbvkdmtor.example to 198.51.100.88 (frame 134 is the answer). The next question for a hunter: did 10.0.0.31 then connect to 198.51.100.88? Not in this capture, so you would pivot to flow records.

05Find the fast-flux name.

dns.qry.name == "secure-login.bank-update.test" && dns.flags.response == 1
Add columns: dns.a, dns.resp.ttl
Answer

10.0.0.14 asks for the same name 14 times over about 8 minutes. Every answer has a TTL of 30 and three different A records, none repeated. A real site keeps stable addresses and long TTLs; a fast-flux name rotates through compromised hosts so blocking an IP does nothing. The name itself (a login page that is about a bank update) is the phishing clue.

06Turn each finding into a rule.

Zeek dns.log: length(query) > 50, or count of distinct subdomains per parent per 5 min
Zeek dns.log: rcode_name == NXDOMAIN, count per orig_h per minute
Zeek dns.log: TTLs < 60 with a changing answer set
Answer

Sketch each as a Zeek or SIEM query and agree on a threshold. Ask: what legitimate traffic trips each rule? (CDNs use short TTLs. Security products and anti-spam tools make long TXT lookups. A misconfigured app can generate NXDOMAINs.) Which of the three would you page someone for, and which would you only report?

Example Suricata rule for the tunnel: alert dns $HOME_NET any -> any any (msg:"CIS53 possible DNS tunnel: long encoded label"; dns.query; pcre:"/[a-z0-9]{30,}\./i"; threshold:type threshold, track by_src, count 5, seconds 60; classtype:trojan-activity; sid:9000001; rev:1;) It matches only 10.0.0.77 in this capture. The same idea as a Sigma rule for Zeek dns logs: logsource: product zeek, service dns; detection: qtype_name TXT and query matches [a-z0-9]{30,}\.. See the Class 3 slides and notes Part 7.
