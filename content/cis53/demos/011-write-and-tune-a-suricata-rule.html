Write and tune a Suricata rule

One 11-minute capture of a small office. Staff upload timesheets to the intranet. One host, 10.0.0.77, also posts a customer file to a new outside name, beacons every 60 seconds, then repeats the upload over TLS. Write a rule, run it, read what it caught, and tune it.

Download and open

  • rule-lab.pcap — 290 packets: intranet pages, two legitimate uploads, six health checks from a script, and the incident
  • class4-suricata.rules — all five rules used below, with comments

01Look before you write.

Statistics > Conversations > TCP
http.request.method == "POST"
Answer

Three POSTs to a path that starts with /upload: two from staff (10.0.0.15 and 10.0.0.23) to the intranet server 10.0.0.50, and one from 10.0.0.77 to 198.51.100.77, a host nobody else talks to, with a 63 kB body. A rule that only looks at the URI cannot tell them apart.

02Write the obvious rule and run it.

alert http any any -> any any (msg:"CIS53 v1 upload"; http.method; content:"POST"; http.uri; content:"/upload"; sid:9100001; rev:1;)

grep 'sid:9100001' class4-suricata.rules > one.rules
suricata -r rule-lab.pcap -S one.rules -l out -k none
cat out/fast.log
Answer

Run one rule at a time: pick it out of the rules file with its sid, as above (9100002 for v2, 9100003 beacon, 9100004 SNI, 9100005 user agent). Three alerts here. Two are staff doing their job, so this rule would flood the queue with false positives. Name the parts: the header is alert http any any -> any any (action, protocol, source, ports, direction, destination); the options in the brackets are the message, two content matches (each with a sticky buffer, http.method and http.uri) and the sid.

03Tune it: say who, which way, and where in the URI.

alert http $HOME_NET any -> $EXTERNAL_NET any (msg:"CIS53 v2 upload to outside host"; flow:established,to_server; http.method; content:"POST"; http.uri; content:"/upload"; startswith; classtype:policy-violation; sid:9100002; rev:2;)
Answer

One alert, at 09:01:00, 10.0.0.77:52001 to 198.51.100.77:80. What changed: $HOME_NET to $EXTERNAL_NET removes the intranet uploads; flow:established,to_server keeps it to requests; startswith anchors the match; classtype sets the priority. Bump rev every time you change a rule. This is the tuning loop: run on known-bad and known-good data and read both lists (Roddie Ch. 2, Test phase).

04Add a beacon rule with a threshold.

alert http $HOME_NET any -> $EXTERNAL_NET any (msg:"CIS53 beacon: repeated GET /check"; flow:established,to_server; http.method; content:"GET"; http.uri; content:"/check?id="; startswith; threshold:type threshold, track by_src, count 5, seconds 600; classtype:trojan-activity; sid:9100003; rev:1;)
Answer

One alert, from 10.0.0.77, once the fifth /check?id= request lands. A single GET to that path would be ignored. Try changing count to 9 and see the alert disappear: eight beacons are not enough. A threshold is a tuning knob, and a threshold you set too high is a false negative.

05Try the shortcut: match the user agent.

alert http any any -> any any (msg:"CIS53 python-requests user agent"; http.user_agent; content:"python-requests"; sid:9100005; rev:1;)
Answer

Fifteen alerts: nine from 10.0.0.77, six from the build server 10.0.0.60 polling an internal health API. A user agent costs the attacker nothing to change, and a lot of normal software shares it. It is an indicator at the bottom of the Pyramid of Pain (Roddie Ch. 1); the upload direction and destination are behavior, which is harder to change (Ch. 7).

06Now look at the same upload over TLS.

tcp.port == 443
tls.handshake.extensions_server_name

alert tls $HOME_NET any -> $EXTERNAL_NET any (msg:"CIS53 TLS to files.cdn-sync.test"; flow:established,to_server; tls.sni; content:"files.cdn-sync.test"; nocase; endswith; classtype:trojan-activity; sid:9100004; rev:1;)
Answer

At 09:10:40 the same host sends about 52 kB to the same server on port 443. Rules v1 and v2 see nothing, because the request line and body are encrypted. The SNI, the bytes and the timing are still visible, so a rule on tls.sni alerts. Tradeoff: that is an indicator (a name) and it dies when the attacker picks a new one; the lasting signal is "an internal host with no history sends 50 kB out to a new name". That needs flow data (Demo 12) and baselines.
