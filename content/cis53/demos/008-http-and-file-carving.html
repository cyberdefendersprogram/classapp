HTTP and file carving

A user on 10.0.0.15 clicked a link in mail, fetched an "invoice", and then the machine started phoning home. Walk the story from the packets, carve the files, hash them, and say what you would tell the manager.

Download and open

  • http-carve.pcap — 107 packets: ordinary browsing, a fake image, a zip, and six beacon POSTs

All traffic is synthetic. Hosts use private or documentation addresses and domains end in .test or .example. Nothing in the file is real malware.

01What did this host request?

http.request
Add columns: http.host, http.request.uri, http.user_agent
Answer

Ten requests: four GETs and six POSTs. Browsing to parts.web.test looks normal. Then invoice-portal.web.test serves a .jpg and a .zip, and gate.cdn-sync.test receives six POSTs to /gate.php.

02Which user agent does not belong?

http.user_agent contains "MSIE 6.0"
Answer

The six POSTs say Mozilla/4.0 (compatible; MSIE 6.0; Windows NT 5.1), a browser from 2001, on a host whose other requests say Chrome 130. Two different clients on one machine means a second program is making web requests. User agents are easy to fake, so treat this as a lead, not proof.

03Is the picture a picture?

http.request.uri contains ".jpg"
File > Export Objects > HTTP > save invoice-0412.jpg
file invoice-0412.jpg
Answer

The server says Content-Type: image/jpeg, but the first two bytes of the body are MZ (the header of a Windows program) and file reports plain text, not a JPEG. The 3,082-byte body is a harmless training file. In real traffic this mismatch between declared type and content is the classic sign of a disguised executable. The request carried Referer: http://mail.office.test/inbox, so the user got here from webmail.

04Hash what you carved.

File > Export Objects > HTTP > Save All
shasum -a 256 *
Answer

invoice-0412.jpg: f35d8cea632b2d809da563ea8dd79bae683ed3f9f8cc55cf089a3144572fd09f
q3-report.zip: 9f6d6cf59e463297c6c9d15c2b8ae014111b14a629e7f9d14c14813c1a5a4f5d
logo.png: 297486d0c55438725f277695e0c18bdb7e8755d704fdddb9ff5775a8c7191380

The zip is not a valid archive either (file says only “data”); it is random bytes behind a zip header, just enough to give you something to hash. The six gate.php exports are the small POST bodies and responses.

The hash is the handle you search threat intelligence with. These are made-up files, so VirusTotal will not know them. Say so, and say what you would do next if it did know one.

05Show the beacon.

http.request.method == "POST"
View > Time Display Format > Seconds Since Previous Displayed Packet
Answer

The POSTs arrive at 19, 49, 79, 109, 140 and 170 seconds: every 30 seconds. Same host, same URI, same size (292-byte frames). The server answers cmd=sleep&t=30, which is tasking: the controller is telling the implant how long to wait. Compare Demo 005 from Class 2.

06Decode the POST body.

Right-click frame 51 > Follow > HTTP Stream
echo 'aG9zdD1XUy0wMDQyJnVzZXI9YXJpdmVyYSZzZXE9MCZpZGxlPTA=' | base64 -d
Answer

host=WS-0042&user=arivera&seq=0&idle=0. The implant reports the machine name, the logged-in user and a sequence number. Base64 is not encryption: anyone with a sensor can read it. Now you know who to call and which machine to isolate.

07Write the two-sentence summary for a manager.

Answer

Example: "At 09:00:06 user arivera's workstation WS-0042 downloaded a file called invoice-0412.jpg that is really a Windows program, from a link in webmail. Starting 13 seconds later the machine contacted gate.cdn-sync.test every 30 seconds, which is how an infected machine checks in for orders; isolate it and reset the account." Check that every claim points at a packet number.
