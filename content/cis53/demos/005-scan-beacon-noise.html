Scan, beacon and noise

Twenty minutes of office-like traffic with three things hidden in it. Find them, say which one is malicious, and write the evidence chain.

Download and open

  • scan-beacon-noise.pcap — 3,128 packets, about 20 minutes: web browsing, one scan, one beacon, one long streaming connection

Open the file in Wireshark (File → Open) or run the tcpdump / tshark lines below. All traffic is synthetic and uses private or documentation addresses.

01Start with the big picture.

Statistics > Protocol Hierarchy
Statistics > Conversations > TCP (sort by Packets, then by Duration)
Answer

Mostly TLS and DNS. Two conversations stand out: one host that touched over a thousand ports, and a pair with a very long duration.

02Find the scanner.

tcp.flags.syn == 1 && tcp.flags.ack == 0 && ip.src == 10.0.0.77
tshark -r scan-beacon-noise.pcap -q -z conv,tcp | head -50
Answer

10.0.0.77 sent 1,024 SYNs to ports 1–1024 on 10.0.0.10 from one source port in about four seconds. Closed ports answered RST,ACK; ports 22, 80 and 443 answered SYN,ACK and the scanner reset them. Filter the open ports: ip.src == 10.0.0.10 && tcp.flags.syn == 1 && tcp.flags.ack == 1

03Find the beacon.

ip.dst == 203.0.113.50 && tcp.flags.syn == 1
Statistics > I/O Graph (add that filter, interval 10 s)
Answer

20 connections to port 8443, about 60 seconds apart, each with a 120-byte request and an 86-byte reply. Regular timing and size is the shape of a beacon. In the I/O graph you see evenly spaced spikes.

04Find the long streaming connection.

ip.addr == 203.0.113.20 && tls.handshake.extensions_server_name
Statistics > Conversations > TCP
Answer

10.0.0.5 to 203.0.113.20:443, SNI api.llm-provider.test, about 33 seconds long, 402 packets from the server with a few hundred bytes each. It looks like a heavy conversation, but the shape is different: one connection, irregular timing, and a small request followed by a long streamed response.

05Which of the three is malicious? Defend your answer.

Evidence chain: what you saw, in which frame, what it means, how confident you are.
Answer

Scanner: very likely hostile or a misconfigured tool. Beacon: suspicious, needs the host and process. The streaming call: probably an approved AI service, but check the destination against your allowlist. Streaming responses are a classic false positive for C2.

06AI angle: what would change if the beacon were written with an LLM?

Think about jitter, size variation, destinations and protocol (HTTPS to a popular API).
Answer

A generated beacon can add random jitter and blend into AI or cloud traffic, so strict regularity is the easy case. Baselines per host and an allowlist of AI destinations become more valuable than interval checks.
